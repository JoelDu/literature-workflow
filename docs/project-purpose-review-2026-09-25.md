# 项目目的与实现审核（2026-09-25）

> 修复状态（2026-09-26）：下列八项发现已完成代码修复。本文正文保留审核时的证据；修复实现、验证范围与运行说明见 [修复记录](project-purpose-fixes-2026-09-26.md)。

审核对象：当前整个工作区，包含已有未提交修改。按用户要求关注目的、实际功能闭环和结果可靠性，不评判命名、代码重复等风格问题。本报告没有修改业务代码。

已启动三个 subagent 分别检查入库、综述、引文发现；它们随后均遇到额度限制。入库 agent 返回了初步发现，主 agent 独立核实并接手其余检查。本报告不声称三个独立审核均已完成。

## 判断

项目方向清楚且有实际价值：将 PDF 变成可管理、可检索的科研资产，并据此形成带引用的综述初稿，进一步通过引文发现补充馆藏。批处理、元数据抽取、检索与重排、引用清洗、运行清单及基线校验都有具体实现。无需以大规模重构为下一阶段目标。

主要缺口位于不同入口和不同数据库之间：完成笔记导出、完成图谱入库、能够参加综述检索，目前并不是同一件事。项目适合继续作为有人监督的科研辅助工具；现有代码证据不足以支持“所有入口均已完成同一自动化闭环”的结论。

## 高优先级发现

### 1. 实时处理成功的论文没有进入检索源表

- 位置：`pipeline.py:164`、`:172`、`:209`；`litreview/store.py:152`。
- 实时路径导出笔记和 Excel、归档 PDF、保存去重哈希后调用索引，但没有持久化 `papers` 的正文及 `EXPORTED` 状态。索引只查询该表中符合条件的记录，不读取 Excel 或笔记。
- 结果：新 PDF 可以显示处理成功，却不能用于语义检索或综述；随后手动执行 index 也无法补救缺失的源记录。MinerU 中间正文还会被删除。
- 验证：隔离 SQLite 上，指定一个无 `papers` 记录的文献 ID，`docs_needing_index` 返回空列表；静态追踪确认实时导出路径未写入该表。
- 建议：成功持久化正文和元数据后再标记完成，随后索引；保留后续 enrich 所需解析资产。

### 2. 滚雪球补入的文献未接入通常的综述检索库

- 位置：`litreview/pipeline.py:543`、`:787`；`web_server.py:1493`、`:92`；`mcp_server.py:164`。
- 候选入库将 Work、分块和向量写入 `test_db_path`；Web/MCP 检索使用 `settings.DB_PATH` 的 VectorStore。默认配置将它们分开，没有在该完成路径上建立联合检索或受控同步。
- 结果：候选可以在图谱中成为馆藏、达到 `VECTOR_INDEXED`，但下一次常用 search/generate 仍看不到这些新证据。对“发现文献以改善综述”的目标，这是关键断点。
- 建议：明确生产库与发现库的边界，以联合读取或人工确认后的发布步骤接通；保留生产隔离要求。不可简单合并文件：两条路径的索引元数据 schema 也不同。

### 3. 教材自动索引把 Qwen3 请求发给 OpenAI 生成客户端

- 位置：`daemon.py:82`、`:108`；`litreview/indexer.py:35`；`llm_router.py:21`。
- 定时教材任务创建 OpenAI 客户端，再将同一个客户端传给 `build_index`；索引器直接用它请求配置的 Qwen3 embedding 模型。
- 结果：按默认 OpenAI 端点和 Qwen3 配置，教材正文入库成功后自动嵌入失败，需要另行运行正确的索引入口。
- 建议：索引调用不传生成客户端，使用其已有 SiliconFlow 客户端构建路径。

### 4. 实时额度耗尽会将正常 PDF 当作永久失败移走

- 位置：`litreview/quota.py:45`；`llm_router.py:91`；`pipeline.py:147`。
- 配额不足抛出中文 RuntimeError，实时处理只按若干英文关键词和网络异常类型识别暂时失败，该异常不匹配，进入移动至 failed_pdfs 的分支。
- 结果：达到每日上限后，后续正常文献也可能被移出待处理目录，次日不会自动继续；这不符合文档中的等待下一 UTC 日语义。
- 验证：临时数据库将配额设为零，实际 reserve 抛出的异常经现有判定式得到 transient=False。
- 建议：使用明确的配额异常类型，将文献保持待处理并结束本轮提交。

### 5. Web 的公网鉴权可被客户端伪造转发头绕过

- 位置：`litreview/guard.py:150`。
- 中间件无条件相信 X-Forwarded-For / X-Real-IP，并允许私有地址免鉴权，没有先验证直接连接者是否为可信代理。
- 结果：当服务可被不可信网络直接访问时，请求可冒充本地来源访问文献、配置修改和耗费额度的接口。
- 验证：隔离调用真实中间件，连接来源固定为 203.0.113.9、未提供 token；无转发头返回 403，添加 X-Forwarded-For: 127.0.0.1 返回 200。未请求运行中的服务。
- 建议：只接受已配置可信代理提供的转发信息，其他情况使用连接来源。

### 6. MCP HTTP 服务没有安装远程访问守卫

- 位置：`mcp_server.py:1887`（dual_app 构建）。
- Web 安装了 RemoteAccessGuardMiddleware；MCP 的融合 HTTP/SSE 应用只组装路由和 lifespan，未安装此守卫或配置 FastMCP 鉴权，默认监听 0.0.0.0。
- 结果：如果该端口能被不可信网络访问，设置 REMOTE_AUTH_TOKEN/MCP_AUTH_TOKEN 也不会让此入口执行文档所述 token 检查。实际网络暴露情况未在本次审核中检查。
- 建议：把鉴权接到实际传给 uvicorn 的 MCP 应用，并分别验证两个传输入口。

## 中优先级发现

### 7. Web 综述仍走独立旧流程，缺少 CLI/MCP 的恢复与逐章编排能力

- 位置：`web_server.py:844`、`:1050`；对照 `review.py:804`、`mcp_server.py:1080`。
- Web 先收集所有章节证据，再写所有章节，未调用共享 `generate_review_sections`；任务及进度只保存于进程内 `_jobs`，没有对应的持久化检查点与恢复入口。
- 结果：跨章已引用文献降权等共享编排策略不作用于 Web；Web 服务重启丢失未完成任务进度，用户可能需要重新生成。与 ADR-0003 中各端业务及进度一致的决策不符。
- 建议：Web 接入已有共享编排及任务持久化，而不是继续分别补齐逻辑。

### 8. 发现入库的嵌入失败会写入测试向量，Web 仍显示入库完成

- 位置：`litreview/pipeline.py:774`、`:809`；`web_server.py:1508`。
- 真实嵌入请求失败或不可用时，生产调用路径生成 1024 维哈希占位向量并标记 VECTOR_INDEXED_TEST；Web worker 不检查该降级结果，仍置 completed 并报告成功入库。
- 结果：用户收到完成提示，却没有可用于真实语义检索的向量。底层返回的 is_real_embedding 可以辨别，但完成判定未使用它。
- 建议：测试向量只在显式测试模式使用；实际请求失败应保留可重试状态，界面清楚区分已解析和已完成语义索引。

## 对结果质量的判断与验证边界

引用白名单、元数据清洗、Markdown/DOCX 哈希、manifest 和基线比较有价值，能减少引用编号与产物完整性问题。但这些检查不等于逐项验证论文是否支持生成文本中的数值、因果关系和结论；本次没有进行真实主题的付费生成或学术内容盲评，不能据此评价实际综述已达到投稿质量。

本次采用源码调用链核对、一个隔离中间件复现和两个临时数据库探针。未运行全量测试，未调用收费模型，未读写生产文献数据库，未修改业务代码。文档中的历史馆藏数量和“全绿”统计未作为当前验收结果。

建议验收按三个用户场景推进：新 PDF 经实时/批处理后能被检索并正确引用；发现候选经审批入库后能参与下一次综述；相同主题在 Web/CLI/MCP 上具有一致的证据处理与恢复行为。若开放远程服务，应同时先修复上述两处鉴权问题。
